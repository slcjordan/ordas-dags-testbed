# ordas-dags-testbed

Stands in for a customer's repository. ORDAS opens pull requests here as the
`ordas-dev` GitHub App, and what this repository's CI says about them is
Gate C.

**The name is wrong and is kept anyway.** There are no DAGs here. The
execution target moved from Apache Airflow to GitHub Actions in September
2026 and the generated artifact is a YAML *segment descriptor*; renaming the
repository would break the App installation, two documents' worth of links
and every reference to `testbed#2`, `#3` and `#4`, to correct a word. See
`docs/design/deletions.md` § The fourth override in
[slcjordan/ordas](https://github.com/slcjordan/ordas).

## What is written by hand, and what is not

**`.github/workflows/ci.yml` is written by hand and is the only thing here
that is.** ORDAS *cannot* write it: the App holds `contents: write` and
`pull_requests: write` and deliberately not `workflows: write`, on the
grounds that an App that can edit the test it is being judged by is not being
judged.

That refusal is enforced rather than intended, and it was measured on
2026-09-22: a push that adds a path under `.github/workflows/` fails at
`POST /git/trees` — the first of the three calls a push makes, `403`, before
any object exists. A push of any other path into this repository succeeds,
because enforcement is on the paths a commit *changes* and not on what the
repository contains.

Everything else arrives in a pull request generated by `cmd/ordaspr`.

## Why it exists separately

Gate C asks whether a generated artifact survives a CI that is not ours. A
test suite in the generator's own repository cannot answer that: it runs the
linter we chose, at the version we pinned, against fixtures we wrote. The
point of this repository is that its checks were configured **without
reference to what the generator happens to emit, and then frozen**.

So the checks here should be ordinary rather than accommodating. If a
generated file fails them, the generator is what changes.

The one exception, and it is a real one: `yamllint`'s default line length is
80 characters, and `source_sha256: "<64 hex>"` is 81. No correct descriptor
can be shorter, so that rule is *unsatisfiable* rather than unmet, and
`ci.yml` states 88 with the reason written next to it. Everything else
yamllint found on its first run was the generator being wrong and was fixed
upstream. **A rule relaxed because the artifact cannot meet it is a different
act from a rule relaxed because today's artifact does not, and only the first
one is allowed here.** Anything relaxed says why, in the file.

## What happened to the previous CI

It judged Airflow: `ruff`, `ruff format --check`, `pytest`, and a `DagBag`
parse against a real `apache-airflow==2.10.5`. It was a good judge — the
first thing it ever did was reject an artifact the generator's own gate had
passed, on `UP017`, which is the only reason its verdicts were worth
anything.

It could not judge a descriptor, and it did not say so. Every step read
`dags/` or `tests/`, and `ruff` ignores YAML. Because the generator's push
builds its tree with `base_tree`, a pull request carrying only descriptors
kept the merged Python on the branch — so
[#4](https://github.com/slcjordan/ordas-dags-testbed/pull/4) went **green in
44 seconds having read none of the six files it carried.** It was closed with
that finding on it rather than merged.

The step written to prevent exactly that is the one that failed. `there is
something to check` existed because *"a check that passed because it found
nothing to look at is indistinguishable, from the outside, from one that
looked"* — and it asked whether **something** was present. The replacement
asks whether the thing under review is present, against the merge base, which
is the question that survives a change of artifact.

## Reading a pull request from ORDAS

Each pull request carries, per segment:

| path | what it is |
|---|---|
| `ordas/segments/<process>-<n>-<unit>.yaml` | the segment descriptor — **data**, with no `run:`, no `if:` and nowhere to put one |
| `spine/*.md` | what the segment will *do*, in prose, for a person |
| `evidence/*.json` | what was measured, and what was excluded from the measurement |

**Read the evidence block first.** A pull request whose title says
`[unmeasured]` is one where no shadow window was supplied, which means an
absent agreement rate rather than a clean one. That distinction is the point.

**Then read `spine/`, not the descriptor.** The descriptor says *which* work
runs and the bound on what it may change — scope, actor, the declared write
set down to the field. It does not say what the work does, and approving it
without reading the spine is approving an identity. Its own header says so.

Editing a generated file is not forbidden, it is measured. `source_sha256` in
each descriptor hashes the inputs it was generated from and the evidence block
hashes the file's contents, so a hand-edit moves the second and leaves the
first. A hand-edit you tell us about is worth more than a clean regeneration
that hides what had to change. CI checks that pairing.

## What does not happen here

**Nothing in this repository runs a segment.** A descriptor is executed by a
scheduled workflow the customer writes once, by hand, which claims marked
tickets from the sampler and invokes `ordasrun` — see `docs/execution/` in
the generator's repository for the worked example. There is no such workflow
here, and there should not be: it needs a self-hosted runner reaching a broker
inside a private network, and **this repository is public**. GitHub's own
guidance is to use self-hosted runners only with private repositories, because
a pull request from a fork can otherwise run attacker-controlled code on the
host.

That splits Gate C rather than blocking it. Schema and lint checks run on a
GitHub-hosted runner with no secrets and no trace content, which is what
happens here. Executing a real segment needs a private repository and is a
different measurement. That the artifact can be checked without executing
anything is the point of it being data.
